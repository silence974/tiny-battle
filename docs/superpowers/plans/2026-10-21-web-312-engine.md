# Web 312 Engine and Realtime Game Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a playable Web 312 engine in the tiny-battle project root with one host referee and four Supabase-Realtime-connected player seats.

**Architecture:** Keep `engine312.js` pure and deterministic, with the host browser as the only caller that mutates authoritative state. Use a small `supabase-room.js` protocol layer for anonymous auth, private room broadcasts, seat allocation, ordered commands, snapshots, and resync; keep the browser shell deliberately minimal.

**Tech Stack:** Static HTML/CSS/JavaScript, browser Supabase client from CDN, Supabase Anonymous Auth and private Realtime Broadcast, Node built-in test runner, no build step.

**Spec:** `docs/superpowers/specs/2026-10-21-web-312-engine-design.md`

## Global Constraints

- The formal runtime is JavaScript in the Web app; Python is reference/validation only.
- The root Web app is the delivery target; do not modify `p2p-vote/`.
- There are five parties: one non-player host referee and four player seats.
- The host is trusted and must remain online; Supabase transports messages but is not the rules authority.
- No service-role key, Edge Function, Postgres persistence, host migration, TURN deployment, or final visual polish is part of this version.
- Candidate 312 values are configuration-driven; black-HQ capture is a shared win, forced black action-card termination is a shared loss, and both outcomes include individual score ranking by score, then gold, then controlled non-HQ tile count, with exact ties preserved.
- Black expansion over an unknown tile without an expedition drops the unrevealed event; failed post-black exploration leaves the tile neutral; building is legal on explored empty ground, while production/control/score require stationed control.
- Host-only four-view debugging is allowed; ordinary seat links expose only their bound seat, and concurrent human/Agent commands for one seat resolve by sequence with an explicit conflict rejection.

## Review Focus

- An out-of-turn, stale, duplicate, or resource-invalid command must not mutate host state; Task 1 tests sequence/legality rejection.
- Simultaneous attacks must resolve from the pre-combat board and apply ties/empty defenders/displacement consistently; Task 1 tests combat fixtures.
- A player snapshot must not expose another player's hand or private event choice; Task 1 tests viewer filtering.
- A fifth join, duplicate identity, wrong room, or reconnect gap must leave seat and sequence state unchanged; Task 2 tests protocol handling.
- Missing Supabase configuration/auth/channel failures must be actionable and must not leave a half-started room; Task 3 tests static/runtime seams.
